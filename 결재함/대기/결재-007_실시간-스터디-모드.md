# 결재-007: 4인 실시간 면접 스터디 모드(로그인 포함) 구축 방식

## 결정할 것
스터디원 4명이 각자 계정으로 로그인해 같은 회의실에서 동시에 진행하는 기능을 어떤 방식으로 만들지.

## 배경
- 지금은 혼자 하는 시뮬레이터이고, 서버 없이 브라우저에서만 돈다.
- 동시 접속에는 ① 로그인(계정 확인) ② 실시간 방(접속자·진행 단계·발표·반박 동기화) ③ 기록 저장이 필요하다.
- Notion은 기록 저장소로는 맞지만 API가 평균 초당 3회로 제한돼 실시간 동기화나 비밀번호 저장에는 맞지 않는다.
- 설계안: `03_개발팀/설계/실시간-면접스터디-설계.md`

## 선택지
| | A안 Supabase (권고) | B안 Cloudflare 직접 구현 | C안 로그인 없이 방 코드만 |
|---|---|---|---|
| 내용 | 로그인·계정 DB·실시간 방을 Supabase로. 결과는 Notion에 동기화 | 기존 Notion 중계 서버(Worker)에 Durable Objects로 실시간 방, 로그인은 직접 구현 | 이름+방 코드로 입장, 계정 없음. 실시간은 A나 B 기술 사용 |
| 비용 | 0원 시작 (무료: 동시 접속 200, 월 활성 사용자 5만, 7일 미사용 시 일시정지) | 0원 시작 (무료: 하루 요청 10만) | 0원 |
| 기간(추정) | 1단계 약 1~2주 | 약 3~4주 | 약 1주 |
| 장점 | 비밀번호 해시·재설정·Google 로그인을 서비스가 처리. 개발량 최소 | 서비스 하나로 통일, 세밀한 제어 | 가장 빠름, 개인정보 최소 |
| 리스크 | 외부 서비스에 이메일 저장(처리방침 필요), 무료 플랜 일시정지 | 인증을 직접 만들면 보안 사고 위험과 책임이 큼 | 사칭·기록 관리 불가, 나중에 로그인 다시 붙여야 함 |

## CEO 권고
A안. 오너가 요구한 '아이디·비밀번호 확인'을 직접 만들지 않고 검증된 인증 서비스에 맡기는 것이 가장 안전하고 빠르다. Notion은 결과 기록용으로 유지한다(결재-005).

## 승인 시 다음 행동

- 개발팀: 1단계 구현(로그인, 방 만들기·입장, 접속자 목록, 진행 단계 동기화, 채팅)
- 기획팀: 스터디 진행 규칙(발표 순서, 사람 반박, 상호 평가 기준)
- 홍보팀·개발팀: 개인정보 처리방침·동의 문구 초안
