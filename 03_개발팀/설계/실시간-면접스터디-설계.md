# 실시간 면접 스터디 모드 설계안 (v0.1, 2026-10-20)

## 목표
면접 스터디원 최대 4명이 각자 이름(계정)으로 접속해, 같은 발제·같은 회의실에서 동시에 진행한다.

## 사용자 흐름
1. 로그인 (이메일+비밀번호 또는 Google)
2. 방장이 발제를 골라 **스터디 방**을 만들고 방 코드·링크를 공유
3. 스터디원 입장 → 각자 다른 직무(팀) 선택. 빈 자리는 지금처럼 가상 부서(NPC)가 채움
4. 방장이 시작 → 발제 → 가상 부서 발표(모두 같은 화면을 같이 봄)
5. **사람 차례**: 한 명씩 자기 1장 PPT를 화면 공유처럼 띄우고 발표 (나머지는 실시간으로 봄)
6. **반박은 사람이**: 다른 스터디원이 반박·질문을 직접 입력(또는 가상 부서 반박을 대신 사용)
7. 상호 평가: 각자 다른 사람 발표에 5개 항목 점수·한 줄 코멘트
8. 결과: 개인 리포트 + 스터디 전체 요약 → Notion에 기록

## 실시간으로 맞춰야 하는 것
| 항목 | 방식 |
|---|---|
| 접속자 목록·자리·온라인 여부 | Presence |
| 진행 단계·현재 발표자·타이머 | 방장 기준 상태 방송(Broadcast) |
| 발표자의 슬라이드 | 저장 후 변경 시 방송 (편집은 각자 화면에서) |
| 채팅·반박·질문 | 메시지 방송 + DB 저장 |
| 회의실 아바타 위치 | 위치 방송(초당 몇 회로 제한) |
| 음성·영상 | 1단계 제외. 2단계에 WebRTC(4인 메시) 검토 |

## 백엔드 역할 나누기
- **로그인·계정·비밀번호**: 관리형 인증 서비스 사용. 비밀번호를 직접 저장·비교하지 않는다(해시·재설정·잠금까지 서비스가 처리)
- **실시간 방**: Supabase Realtime(Presence·Broadcast) 또는 Cloudflare Durable Objects
- **기록 저장소**: 세션·평가는 DB에 먼저 저장, 끝난 뒤 Notion으로 구조화해 동기화(결재-005)
- **Notion을 실시간 백엔드로 쓰지 않는 이유**: API 한도가 평균 초당 3회(15분 2,700회)라 4명 동시 진행의 상태 동기화를 감당할 수 없고, 비밀번호 같은 인증 정보를 저장하기에 적합하지 않다

## 데이터 모델 (추가분)
```
users          id, email, display_name, created_at          -- 인증 서비스가 관리
study_rooms    id, code, host_id, scenario_id, status(waiting|running|done), created_at
room_members   room_id, user_id, team_id, joined_at, left_at
room_events    id, room_id, user_id, kind(phase|speech|rebuttal|question|chat), payload, at
peer_reviews   id, room_id, reviewer_id, presenter_id, scores(json), comment
sessions       (기존) + room_id
```

## 보안·개인정보
- 비밀번호는 인증 서비스가 해시 저장. 앱·Notion에는 저장하지 않음
- 방 코드는 추측하기 어렵게(8자 이상), 방장은 강퇴 가능
- 개인정보 처리방침·동의 화면 필요(이메일, 발표 내용 저장)
- 미성년자 가입 제한 문구

## 단계
1. 로그인 + 방 만들기·입장 + 접속자 목록 + 진행 단계 동기화 + 채팅
2. 사람 발표·사람 반박·상호 평가, Notion 동기화
3. 음성·영상, 녹화 없는 실시간 대화
